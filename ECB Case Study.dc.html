Chapter One

200 km. 200 booths. No existing system to handle a single call.

My company was contracted to digitise a 200 km stretch of the Delhi–Mumbai Expressway — Gurgaon to Dausa — as part of NHAI's Automated Traffic Monitoring System. The Emergency Control Box (ECB) module was one critical piece: 200 physical roadside telephone booths, one installed every kilometre.

When a highway user operates a booth about an accident, breakdown, or medical emergency, the call rings the nearest NHAI control room. An agent answers, gathers incident details, coordinates with field teams, and dispatches the nearest help. The module had to support this entire workflow — for both agents and supervisors — with no existing system to build on.

On other Indian highways the pattern was the same: emergencies meant calling police (100) or a national helpline. No dedicated infrastructure, no highway-specific response system. Everything that had to happen when a booth rang — identifying location, understanding the incident, coordinating dispatch, logging the interaction — had to be designed from scratch.

For the first time, a control room agent would need to —

01Know which booth was calling and exactly where it sat on the highway — before the call was even answered
02See all simultaneous incoming calls and triage them — not pick up blind with no context
03Surface the nearest ambulance, police, and patrol contacts by location — not recall them from memory
04Keep a permanent record of every call, answered or missed — nothing could be allowed to simply disappear
05Close a prank call with a structured, auditable path — without the risk of discarding a real emergency
06Link every call to a downstream ticket and audit trail — so what was said connected to what was dispatched

The goal

Design the ECB module from scratch — enabling agents to receive incoming calls, identify caller location and incident type, coordinate emergency response, and maintain a complete real-time record of every call. Two views: agent, and supervisor with team-level oversight and performance trends. The risk wasn't careless agents. It was giving agents no system to be careful with.

Mapping both journeys surfaced the structural similarity to customer support call centres — an agent receives a distressed contact, gathers information, coordinates a response, and closes the loop. We studied Freshdesk and AWS Support to understand dashboard structure, what agents need at different moments, and workflow sequencing.

Then we identified where the ECB context diverged. Location is mission-critical and can't be typed in later — it has to be visible before the call is answered. Communication is one-directional with no callback option. And the platform is tied to NHAI's own surveillance infrastructure (VSDS, TMCS, VIDS) — no equivalent exists in B2C support tools.

A second close read of the PRD revealed a supervisor layer we hadn't scoped for. We designed the supervisor view first — team-wide call metrics, agent status, hourly trends — then narrowed into the agent view, which shows personal workload only.

A thing I got wrong early

My first instinct was to start with the call list — how calls display, how tabs separate answered from missed, how agents search the log. I spent the first week on this. Then I re-mapped the full agent journey step by step and found the real problem wasn't in the list. It was in the 30 seconds after pickup: where is the caller, what exactly happened, who is closest to help. I threw away that work and restarted with the call detail screen.

Chapter Three

Three directions for the call detail screen — the most critical decision in the flow

The call detail screen had to serve multiple simultaneous needs — capturing incident details, accessing location context, and identifying the nearest help — all at the same time, all on an active call.

Direction A — Rejected

Step-by-step form

Serialised tasks agents need to do simultaneously. You can't wait for the map until after logging the caller's name when a life may be at stake.

Direction B — Rejected

Full-screen map

Better location awareness, but buries the incident form and emergency contacts — both needed at the same time as the map, not after scrolling.

Direction C — Chosen ✓

Parallel split view

Incident form on the left, live map and nearest emergency contacts on the right. Agents can log while scanning — no switching, no recall under pressure.

The parallel split view won because it matched what agents actually needed to do simultaneously — not sequentially. Every other direction assumed agents could finish one task before starting the next. On an active emergency call, that assumption was wrong from the start.

Chapter Four

Five features, each mapped directly to a gap in the workflow

Every design decision in the ECB module was traceable to a specific operational failure in the manual process — not to what seemed useful in the abstract.

Feature 01 · Live Incoming Call Panel

Triage before pickup — see what's ringing, where, and how many

A persistent panel shows all ringing ECB calls in real time. Each card surfaces the device ID and location before the agent picks up. The call list captures every call — answered, missed, or flagged — with a unique ID and a searchable log across all agents.

Device ID and location visible per card before pickup — replaces the completely blind answer workflow.

Multiple simultaneous rings expand into a callout card — agents formally claim a call via the "Attend this call" modal.

Every call gets a unique ID and is searchable across the full team log.

Multiple ECBs ringing — device ID and location visible before pickup

Search across all calls — MISSED badges inline, no tab switching needed

Feature 02 · Location-First Call Detail View

The system surfaces what the caller can't — before the conversation starts

The moment an agent opens an active call, they see the ECB device ID, package number, booth location on a live map, and nearby surveillance devices (VSDS / TMCS / VIDS) — all before speaking. For inactive calls, the same screen switches to a full record view with linked ticket details. One screen serves both moments — no navigation, no context-switching.

Active call — live device location, nearby surveillance devices, incident form, and emergency contacts on one screen

Feature 03 · Nearest Emergency Resources, Auto-Surfaced

No second phone call — dispatch from the same screen

Based on the caller's package location, the system automatically surfaces the nearest ambulance, police, and patrol contacts, along with nearby ADAS vehicles with distance. Agents coordinate and dispatch without leaving the active call screen. For completed calls, the right panel switches to the linked ticket — status, priority, assigned team, and evidence.

Nearest ambulance, police, and patrol contacts pre-populated by package number — no manual lookup under a live call.

Nearby ADAS vehicles shown with distance — the closest response identified without coordination overhead.

Active call panel switches to the full ticket record on completion — one screen, two roles.

Nearest emergency contacts auto-populated by package · Ticket details on completed calls

Feature 04 · Mark as Fake Call

A fast exit for prank calls with a permanent audit trail

Prank calls were flagged as an operational problem in the NHAI PRD. Agents needed a quick path to close them without the risk of accidentally dismissing a real emergency. The "Mark as Fake Call" CTA auto-disconnects the call and logs it with its own detail page — device ID, call recording, agent notes, duration — fully recoverable and auditable, attributed to the agent who closed it.

"Marked as Fake Call" badge in header · Full call record preserved for audit

Feature 05 · Attend This Call + Ticket Integration

A claim mechanism for busy queues and a record that outlasts the call

When multiple calls ring simultaneously, agents expand the callout and confirm pickup via a modal — a formal claim that prevents two agents from unknowingly picking up the same call. Every answered call can generate a ticket directly from the detail view via "+ Create Ticket", linking into the Ticket Management module with ECB ID, recording URL, incident type, and agent notes pre-populated. Missed calls persist in their own tab — nothing drops off the queue, nothing requires memory to track.

Missed calls tab — every unanswered call logged and recoverable

The qualitative shift that mattered

When the PM walked NHAI officials through the platform, the call detail screen — specifically the location map auto-populated before pickup — was the moment the room changed. A senior official asked how many ECBs could ring simultaneously and whether all of them would surface location. That question wasn't about metrics. It was about trust. A map that loads before an agent speaks is a different kind of system than one that asks a panicking caller where they are. That's the gap this closed.

Chapter Six

What I'd approach differently

01Get into the environment before the first wireframe. All early understanding came from the PRD and analogous research. A single shift in a real control room would have surfaced the noise, multi-screen reality, and parallel-call pressure much earlier — the split view was a late insight that should have been day one.
02Be in the room when the client walkthrough happens. The handoff went to the PM, who walked NHAI officials through the product. Design rationale gets lost in translation. I'd push to be present at that walkthrough, or establish a feedback channel that routes responses directly to the design team.
03Build the design system from day one on greenfield projects. Components were designed in phases across a large multi-module platform. Small inconsistencies in spacing, icon sizing, and border radii crept in and required a cleanup pass at the end.
04Operational products are won on clarity, not craft. The decisions that determined success — what's visible before pickup, whether the map was readable at a glance, whether the interrupt was impossible to miss — were entirely about information hierarchy. Polish came second.

Chapter Seven

The first module in a 10+ module platform — designing it first set the pattern for everything after

The same control room that handled ECB calls also monitored live traffic, managed variable message signs, tracked vehicle speeds, and handled facility incidents — all through the same NHAI ATMS. Designing the ECB module first meant establishing the design language everything else inherited: the dual-role view model (agent vs. supervisor), the information hierarchy for time-critical workflows, and the split-screen pattern that puts all decision-critical content on one screen.

A note on the VIDS case study: VIDS (video incident detection) is the sibling module from this same platform, written up separately because the design problem is genuinely different — operator dashboards for continuous multi-stream alerts, not agent workflow for one-to-one emergency calls. Treat them as one engagement with two modules.

What this phase taught me

Designing the ECB first — before any other module — meant every decision had to work without a reference point. That constraint turned out to be clarifying. It forced the dual-role view model, the split-screen hierarchy, and the information-first approach to become explicit, not implicit. Every module that came after had those principles baked in from day one, not retrofitted. Starting with the hardest, most human-facing piece of the platform was the right call.
